# RidePlay 0.3.1 公开测试版发布说明（草稿）

候选版本为 `0.3.1`，versionCode 为 45，拟使用 tag `v0.3.1` 并在 GitHub 标记为预发布；尚未上传 Release。原 `0.3.0` / 42 仍是历史归档候选。

## 主要内容

- 在禁用 CarPlay 本地音频输出时，可选择发布 Android 媒体会话，转发媒体按键到 iPhone。
- 新增默认关闭的“媒体按键选路引导（实验性）”。收到有效 iPhone 曲目信息或用户返回 CarPlay 后，短暂播放零采样数据并释放，帮助部分 ROM 选择 RidePlay 为媒体按键目标。
- 该实验启用时登记 RidePlay 自身的媒体按键接收器，修复实测 ROM 在进程重启、覆盖安装后遗留旧蓝牙播放器对象的问题；无有效会话时不会因广播自行连接。
- 更新检查改为 RidePlay 自己的 GitHub Releases，并清理旧版本缓存的上游 DiPlay 更新。
- 设置备份纳入 RidePlay 媒体控制／选路引导、拼音、屏幕方向和歌手规则，导入时校验类型；配对密钥等敏感项不随设置迁移。
- 保留不含协议载荷的 iAP2 命令摘要与未确认包诊断，便于导出报告定位连接阶段；撤回临时跳过订阅及未部署的发送节奏实验，使用原有完整协议订阅。

## 实测范围

用户在 2019 KTM 390 Duke、红米 Note 9 Pro 移植版 HyperOS 组合上连续多日反馈车把按键操作正常。电脑旁还完成了媒体按键、暂停恢复、播放器抢占、进程冷启动和覆盖安装的针对性检查。其他车型／ROM、仪表全部文字显示、头盔完整音频路径及所有后台场景不由这些结果自动覆盖。

2026-11-14：同一红米、iPhone14,7（对端自报 iOS 27.2.1），系统热点与 App 保存描述同时设为 WPA2 后，test2 与恢复完整订阅的 control2 都完成自动 AirPlay、运行隧道及画面首帧。control2 这次连接记录约两分钟，未见连接错误或重试；它不是 0.3.1 / 45 候选的安装验收，也不替代重连、实车按键和音频路径验证。

同日用户进一步确认 0.3.1 / 45 候选覆盖安装后连接正常，App 内断开重连、红米重启后打开 App 再连接也均正常。此部分为用户实测反馈，不是新候选的日志或 ADB 验证；不扩大为后台自动连接、所有断网恢复或本候选实车音频／按键路径验收。

2026-11-15：用户对最终 0.3.1 / 45 候选进行多次测试，并明确确认实车车把播放／暂停／切歌、iPhone 到头盔的音乐输出均正常。本轮目标功能验收通过；Siri／电话等未被明确确认的音频路径，以及其他车型／ROM，不由此自动覆盖。

## 使用与已知问题

- 选路引导默认关闭，在高级设置的视频与音频中开启，需要无音频媒体控制及禁用 CarPlay 本地音频输出的实际连接组合；保存后重连生效。
- 返回 CarPlay 可能接管其他 Android 播放器的媒体按键。关闭并重连后停止后续引导，但不会恢复 Android 历史上的上一播放器。
- 仪表播放／暂停图标可能一直显示播放三角形；实车按键功能正常，此显示问题暂缓处理。
- 红米移植 HyperOS 的本次组合在 WPA3／过渡模式尝试中连接失败；两处 WPA2 后恢复。遇到相同故障可用系统热点及 App 描述均为 WPA2 做对照，名称、密码须一致。尚未确定 WPA3 具体失败层，不宣称所有设备都不支持 WPA3，也不自动修改用户系统热点。
- 不需要 Root。

## 安装及发布前须补齐

正式包名 `com.chiccccken.rideplay` 与既有 `.debug` 测试包不同，会并存安装，不是测试包的覆盖升级。应先备份设置，再按最终包名和签名验证升级路径。

已安装同正式签名的 `connection-test2`／`connection-control2` / 44 用户可覆盖安装 0.3.1 / 45，保留应用数据；覆盖安装会结束当前 CarPlay 会话，需要重连。历史 debug 包保留，测试时只运行一个接收器 App。不要为此清数据或删除 iPhone 上跨设备共用的车辆记录。

发布需包含可实际连接 iPhone 的 standalone 主 APK、准确的 `SHA256SUMS.txt`、对应源码提交及许可证。一个更新目录不混放 debug、正式版和示例应用 APK。源码 CI 包不包含独立连接所需的本地运行时材料，不能直接充当公开使用包。
