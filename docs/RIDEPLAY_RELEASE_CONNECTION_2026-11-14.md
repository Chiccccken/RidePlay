## 已知事实

- 用户反馈：新版能看到设备，但连接失败或一直连接中。尚无本次失败日志，具体失败阶段未确定。
- 已安装的是 `com.chiccccken.rideplay` 0.3.0 / 42；旧实测版是独立的 `.debug` 包。安装完成时未启动新包、未迁移设置或执行新包连接验收。
- 本轮只读 ADB 清单没有红米 `bf7b20d`，不能远程读取它当前的权限和连接日志。
- 候选 APK 中的两份本地认证资产与旧实测 APK 逐字节一致。这只排除了打包遗漏／内容不同，不证明新版进程加载成功或 iPhone 已接受认证。
- 两包连接相关的权限声明相同；差异是 debug 的 BYD 仪表权限与随包名变化的应用自有权限。不能由声明推断新包已获得运行时授权。
- 已归档的旧包系统状态显示，本地网络、附近 Wi-Fi、蓝牙连接权限均已授予。新包当前授权未知。
- 旧设置使用 MANUAL 热点，保存了非空名称和密码。新版首次安装也默认 MANUAL，不能声称默认模式改成了 Wi-Fi Direct；但新包没有继承旧包的热点详情。
- `loadIdentity()` 在无私有设置时生成新的 AirPlay 身份；应用内配对记录与 Android 蓝牙配对设备列表是两层状态。看到旧蓝牙设备不证明新版已有 CarPlay 配对状态。
- 两包都含原生库；arm64 的热点辅助与 I2C 库二进制不同，音频库一致。仅凭 Debug/Release 二进制差异不能认定连接回归。

## 当前假设与最小实验

优先核查独立包的首次连接配置、权限及配对状态，保留认证／网络流程回归的可能，不根据现象直接修改连接代码。

1. 若尚无本次日志，先在新版失败后返回“设置 → 诊断 → 保存诊断报告”。已有代码保存连接阶段和会话日志，无需 Root、ADB 或开启屏幕调试日志。报告默认保存在 Downloads/DiPlay。
2. 在同一地点、同一 iPhone 与相同热点状态下，只运行旧实测版连接一次，记录能否成功；再结束旧版连接，避免双应用争用蓝牙或监听端口。
3. 核对新版“设置 → 连接 → 连接设置”的热点模式及已保存名称／密码与红米当前系统热点一致，以及系统应用权限中的附近设备、本地网络访问。只更正实际不一致项，不改系统热点配置。
4. 新版只重试一次，保留失败页面及诊断报告。不要同时更改音频、选路引导、热点模式和 iPhone 配对，避免丢失因果边界。

需要从报告区分的边界：应用启动／认证装载、热点就绪、蓝牙 RFCOMM 建链、iAP2/MFi、首次 TCP、AirPlay 配对、视频开始。缺少实际失败记录时不把任何一项写成根因。

用户可将新版报告放入其 NextCloud 的 `RidePlay-APK-20261114` 文件夹，电脑端同步后即可分析，无需回家连接 ADB。报告虽有脱敏逻辑，仍按私有诊断资料处理。
